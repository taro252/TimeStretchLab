# Phase 50 — 停止耐性と安全な速度変更応答の比較

## 結論

**先行16,384は停止耐性を改善する研究候補。ただし応答遅延が増える条件があるため、標準Aを維持する。L1は処理済み状態を保護したまま一部条件を短縮できたが、過渡音保護が支配する約1.4秒の待ち時間を一律には解消しなかった。正式統合は行わない。**

実機の停止注入15件、応答比較12件、独立オフライン8件、絶対時刻模擬5件に限定した。新しい音質処理、TimeMapのランプや保護幅、safe-densityの判定条件は変更していない。L2は未実装。

ユーザーはMIX/Drumsのt1.85の現行/L1比較を試聴し、**「違和感なし」**と回答した。これは今回の比較に対する評価であり、すべての負荷・音源に対する製品採用承認ではない。

## 1. 親スクリプトの終了判定

`phase49_long.py`は、子の品質終了コード2ならログを保持して次の条件へ進み、全条件終了後にFAIL/INDETERMINATEを親の終了コード2へ反映する。異常終了、集計欠損、行数不整合、必須CSV/判定欠損、子の終了コードと品質の矛盾は構造エラー3とする。正常は0。工程完走と音声合否は別フィールドへ保存する。

全PASS、1件FAIL、全FAIL、INDETERMINATE、子SIGKILL、集計欠損、CSV欠損の障害注入で期待どおりの終了判定を確認。故意の障害検出成功は実機音声PASSではない。保存済みPhase49の3条件も読み取りだけで再検証してPASS、元レポートと元ログは変更していない。新規デフォルト保存先はPhase50、既存保存先での再実行は拒否する。

## 2. 条件と保存

A/B/Cは**先行量のラベル**。すべてFIFO16,384、生成2,048、継承QoS。A=12,288、B=14,336、C=16,384。Phase49のQoS候補Bとは異なる。48kHzでは256/298.667/341.333ms相当。容量倍増DはPhase49で容量だけでは効果がなかったため追加しなかった。

既存Drumsの30秒PCM切出し、MIXの既存区間30秒を使用。Drumsは48kHz、MIXは44.1kHz、2ch float32。独立`phase50_play`はPhase43の検証用プレイヤーを別ターゲットとして構築し、通常のPhase43と正式Phase30/36を置き換えない。ゲインはraw DSPへ混入しない。

装置ID72、出力48kHz、ハードウェア512フレーム。DrumsのSourceNode要求512、MIXはSRC上流471。CPU競合の実機条件は既存busy2スレッド。全実機試験は消音で実際のAVAudioEngine callbackを使用し、参照合成は停止後に行った。新旧WAVの有音評価はユーザーが別途実施した。

装置バッファを64/128/256/1024へ指定しても、別プロセスで取得した値は512のままだった。設定APIは成功を返したが、この指定方法では保持を確認できなかった。装置そのものの能力は断定せず、これら4量子の**実機検証は未実施**と記録する。終了後512を再取得した。模擬試験とは分ける。

最初の注入ドライバーは量子64の設定不一致で停止（exit1）。12件の証拠を保持して再開し、未保持の4量子を記録し、低残量2件と別位置の512/高負荷1件を完了した。元manifest・再開理由・各バイナリSHAを保存する。長尺10分の追加反復とSystem Traceは実施していない。

## 3. 停止耐性

停止はFIFO公開直後、指定出力位置以上かつ指定残量を観測したときに注入する。通常試験の位置は出力4.5秒以上。停止の開始/終了mach、実残量、wall/CPU、次の公開、callback、再充填、EOSを保存する。全15件で注入、有限性、計測、CSV、PCM/EOS、需要量と残量による不足予測の照合が成功した。**音声8 PASS / 7 FAIL、障害検出15 PASS**。FAILを消していない。

| 停止ms | A不足frames | B不足frames | C不足frames | C次の供給までms |
|---:|---:|---:|---:|---:|
| 200 | 0 | 0 | 0 | 209.780 |
| 250 | 0 | 0 | 0 | 260.023 |
| 300 | 2,560 | 512 | 0 | 309.952 |
| 350 | 4,608 | 2,560 | 512 | 359.706 |

Aの250msは最低512framesでほぼ余裕なし。Cの300msは最低2,048frames、350msは512frames不足（最大連続10.667ms）。停止だけではなく、再開DSPと次の公開まで約10msが加わる。成功した停止時間を保証値としない。

| 高CPU負荷の追加条件 | 停止前実残量 | 停止ms | 不足frames | 目標先行量への回復ms |
|---|---:|---:|---:|---:|
| A / 出力6.25秒以上 | 8,192 | 250 | 3,584 | 123.302 |
| C / 出力6.25秒以上 | 12,288 | 300 | 2,048 | 128.972 |
| C / 出力13.50秒以上 | 16,384 | 300 | 0 | 41.304 |

低残量2条件は、先にFIFOを指定残量まで消費させてから停止する診断用条件。事前に補充を止めた区間も公開時系列に現れるため、満杯条件と同じ供給空白とは扱わない。Cの設定でも実残量12,288で300ms停止なら不足し、満杯16,384/別位置13.5秒/高負荷なら不足0だった。注入・回復窓以外の不足は15件とも0。

15件ともPCM消費長=最終出力長、提示時間軸=出力長＋不足frames。ゼロ埋めをrawへ混入せず、提示時間軸を巻き戻していない。FIFO曲線・次の供給・回復時間は各`stall_fifo_timeline.csv`と診断JSONに保存。

通常負荷4件ずつのプロセスCPU秒中央値A/B/C=6.060/6.052/6.081、最大RSS=39.750/39.750/39.578MiB。全注入のcallback最大は0.951ms（予算10.667ms以下）、期限超過・host/sample異常・callback C++確保・書込み拒否0。最悪公開間隔約360msは故意の350ms停止に対応し、自然なOS停止の改善とは呼ばない。

## 4. 64〜1024の絶対時刻模擬試験

C/300ms/満杯16,384/0.40→2.00、busy4スレッド70%条件。理論期限を守って消費し、不足時にワーカーを待たず、起床遅刻による提示期限の逸脱を別計数する。PCMは独立参照へ後で照合した。

| callback | 不足 | PCM | 時間精度 | 全体実時間 | 最大起床遅刻ms |
|---:|---:|---|---|---|---:|
| 64 | 0 | PASS | VALID | PASS | 0.697 |
| 128 | 0 | PASS | VALID | PASS | 1.639 |
| 256 | 0 | PASS | INVALID | INDETERMINATE | 57.085 |
| 512 | 0 | PASS | VALID | PASS | 2.720 |
| 1024 | 0 | PASS | VALID | PASS | 5.089 |

256は起床最大57.085ms、逸脱14スロットでINVALID。不足0でも供給判定/全体はINDETERMINATE、最終照合スクリプトexit2。これをDSP不足と数えず、実時間PASSにも含めない。5件のraw PCMとEOSはすべて一致。実機の未保持量子の代替証明にはならない。

## 5. L1：依存境界の精密化

まず既存方式を使う12件の停止試験に読取専用の旧/精密境界診断を追加した。通常の境界と診断の旧境界が完全一致することを実行時に検査した。縮小できる余裕が観測されたため、独立L1を有効化し、オフライン8件の全PCM一致を確認してから実機へ進んだ。

| 要素 | L1の根拠 |
|---|---|
| 処理済みFFT/位相のTimeMap | 各実解析位置で使ったノードを保持。非整数ノード位置は補間の両端を保持する。実際の直近フレーム出力座標も検査する。 |
| 既に消費したOLA | 各リングの次の未確定絶対位置を取得。次の未処理フレームをその前へ配置する候補は拒否する。 |
| 処理済みFIR | 次の未処理source block位置を取得。raw source nとOLA n＋FFT/2の関係からLP250は4,096、LP3500は2,048のpaddingを保護する。LP250の4,096は必要であり削除しない。 |
| 解析密度 | 常に次のカーソルから通常hop1個先まで一律保護する余裕を外す。ラッチ済みの次カーソルを変更せず、挿入済みフレームを戻さない。密度位置は従来のPhase42実履歴/窓重み判定を引き続き通す。 |
| 公開/準備済みPCM | 全境界の最大値へ含め、再合成/上書きしない。独立最終履歴のPCMと逐次出力全体が一致することも確認する。 |

実際の入力カーソル、処理済み位置、OLA/FIR境界、旧/精密fence、最初の可変/安全ノード、保護延期、密度位置はreplayへ保存した。新候補の全処理済みノードと最近24フレームの座標を実データへ照合し、次のフレームが確定OLAへ侵入したらRejected。位相/OLA/FIRをリセットしない。実機12件のガードにおける実OLA重みと予測の最大誤差は3.476e-7（従来の許容1e-4未満）だった。

`phase50Boundary`の精密値は、この実装の依存に基づく共通時間軸の下限候補であり、あらゆるDSP構成での最小値の証明ではない。`phase50_play`/`phase50_sim`だけでopt-inできる。通常のPhase43はこの環境変数からL1を有効化できない。

## 6. 方向別応答と先行量の副作用

出力要求1/6/14/22秒、および1.85/6.85/14.85/22.85秒で2.00/0.40/1.00/2.00を要求。各音源・タイミングでA、C、C+L1を順次比較、12実機試行/48変更。全件で音声/計測/CSV/有限性/PCM/EOS正常、不足・書込み拒否・期限超過・callback C++確保0。

以下は**要求→TimeMap適用ノードのHAL基準推定提示**の中央値/p95（ms）。各セル2件なのでnearest-rank p95=最大。中央値は中央2値の平均。

|---|---:|---:|---:|---:|
| drums / A | 1004.3 / 1397.2 | 582.6 / 728.1 | 1195.5 / 1535.9 | 789.9 / 929.4 |

| drums / C_L1 | 970.7 / 1397.1 | 631.1 / 728.4 | 1033.8 / 1536.2 | 606.4 / 651.0 |
| mix / A | 1199.7 / 1626.0 | 530.8 / 536.9 | 1488.3 / 1977.5 | 628.5 / 722.5 |
| mix / C | 1200.0 / 1627.2 | 704.7 / 714.5 | 762.2 / 831.5 | 725.1 / 805.0 |

先行量だけで単調に遅延が増減するわけではない。Drums t1.85の.40→1.00はA855.1→C1,180.2msと悪化。一方、MIX t1の同方向はA1,977.5→C831.5msだった。前の要求の適用位置が変わると、後続要求の入力位置/イベント/速度履歴も変わる。後続差を単独の境界削減効果と誤認しない。

同じ先行Cとの比較でL1はDrums t1.85の.40→2.00を677.9→544.4ms（約133.6ms短縮）、.40→1.00を1,180.2→531.4ms（約648.8ms）、1.00→2.00を893.8→561.8msへ短縮した。MIX t1.85の.40→1.00は692.9→618.3ms（約74.6ms）。ただし要求t1ではDrums約1,397ms、MIX約1,627msの.40→2.00はほぼ不変。

最初にraw PCMが変わる位置は適用ノードと別に検出した。Drums t1.85の.40→1.00はCの推定約1,187.3ms→L1約504.7ms、MIX同条件はC約684.8ms→L1約603.4ms。raw差分が公開/準備済みPCMより前に現れないことを全12件で確認した。各具体座標とHAL推定は行別JSON/`statistics.json`へ保存する。

推定式は有効mHostTime＋callback内sourceフレームoffset＋装置のみのpresentationLatency−操作mach時刻。SourceNodeはHALのIOProcを直接観測したものではなく、MIXのSRC遅延は近似を含む。音響ループバック未実施で、実測可聴時刻とは呼ばない。

## 7. 音質とL2の扱い

同じ入力座標を中心とする32領域についてPhase42系のピーク、差分、RMS変動、スペクトル変動、L/R相関、Side/Mid、IPDを計測した。全体NaN/Infなし、raw最大1.412571、共通ゲイン0.5で最大0.706286。個別音量正規化/ピーク制限はしていない。

最大局所sample derivativeは現行/L1とも0.829265。t1.85/第3変更のDrumsピーク0.917/0.914、L/R相関双方約0.993、Side/Mid0.083/0.082。MIXはピーク0.992/1.000、相関0.880/0.882、Side/Mid0.255/0.254。数値だけでクリック/定位/アタックの合格を判断しない。

最大ピークを基準にした3dB幅/前後20ms比は**局所診断proxy**であり、真正のイベント開始位置や前響き量そのものではない。時間写像や演奏内容で比が大きく変わるため、差だけで改善を断定しない。素材の自然な減衰と試聴を優先する。

新旧8本の試聴WAVは`audition/`に共通固定ゲイン0.5で保存。特に`drums_t1p85_current.wav`/`drums_t1p85_L1.wav`、`mix_t1p85_current.wav`/`mix_t1p85_L1.wav`を比較する。要求は1.85/6.85/14.85/22.85秒で、適用/音声差分はその後となる。ユーザーの回答は「違和感なし」。

**L2は未実装。** 今回の主な開始遅延はランプ前の確定境界と最初の安全区間にある。進捗の出力時間化は遷移完了/Busy期間を短縮する可能性があるが、開始前の保護延期を直接解消しない。限られた実験規模では先行量と単一因子L1の検証を優先した。Phase41の早すぎる密度変更を再導入せず、L2を別候補として比較するのは次段階の判断とする。

## 8. 回帰・最終ビルド

Golden25/25は入力/出力SHAの照合を維持。低速B/高速B/Phase41遅延密度/Phase42 safe-densityの202音声は読み取りで在庫SHAを記録し、既存回帰も実行した。在庫SHAだけを新たな音質合格基準にはしない。

注入15/15＋応答12/12のnative raw PCM、オフライン8/8、模擬5/5は同じTimeMap/密度/要求履歴の独立参照へ全サンプル一致。音声FAILや時間精度INVALIDでも、PCM一致の判定と分けて保存する。新規mono/stereo L1テストも接頭部を含む全波形/EOSを照合した。Drums t1.85のL1実機履歴を1,024/2,048ブロックで再合成し、両者と独立参照WAVのSHA-256も完全一致した（`block_regression/result.json`）。

**最終変更後の全CTest65/65成功、384.20秒、exit0**。実行前後のソース指紋も一致した。ビルドRelease/arm64、基準コミットc278f7c。最終ソース指紋`6c606dbb27d085e728f26705aade2590fe6bb3d045ff9f0e3e95ab59fb1e9789`。CSV列の追記前後で2種類のnativeバイナリを使ったため、注入初期manifestと再開後行別SHAを区別する。応答比較は1つのバイナリで実施した。

## 9. 採否と次段階

- **既定はAを維持。** Cは300ms停止耐性の候補だが、低残量では不足し、350ms保証もなく、方向/履歴で応答が悪化する。
- **C+L1を研究候補として保持。** 一部に明瞭な短縮、全PCM一致、今回のユーザー評価良好。すべての要求タイミング・高負荷・素材の応答悪化なしを証明していないため、既定化/正式統合は保留。
- B先行14,336は中間的耐性だが300ms不足を残す。D容量拡大だけは追加しない。QoSも変更しない。
- 次はC+L1で制御停止/高CPU負荷と要求のイベント前後を交差させ、特にMIX 2.00→0.40の約170ms悪化とDrums約1.4秒の残存延期を調べる。同じ実フロンティアでの反実仮想計画比較を追加すると、後続履歴の効果を切り分けやすい。
- L2を行うならL1と同時に変更せず、ランプ終了と密度変更を別々に計測し、Hann²/攻撃音/既存異音解消を再確認する。

正式Experimental 3500、Phase30/36、キャッシュ・シーク、Goldenは変更していない。0.25倍速の研究は再開しない。OS停止の原因特定・長尺の普遍的安全性・操作応答の一律改善は未解決。
