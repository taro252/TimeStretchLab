# Phase 17 — 高速シーク方式の設計・独立試作

## 結論

既知ファイル・0.50倍速では、**Golden相当のraw float PCMキャッシュを第一候補**とする。45秒入力のMIXを0.50倍速で生成したキャッシュはGolden WAVとファイル全体でSHA-256一致し、任意位置からの16,384フレーム先行蓄積後も照合したサンプル差は0だった。現行の先頭からDSP再実行するPhase 16シークは、キャッシュがない・無効・破損している場合のフォールバックとして残す。

DSP状態チェックポイントは理論上raw一致を維持できるが、現行の3解像度処理・OLA・2系統のFIRの進み具合を同時に保存しなければならない。正式DSPを変更せずに正しい状態を取り出すAPIは現時点でないため、今回は設計評価に留める。**チェックポイント方式のGolden一致・実測シーク時間は未検証**であり、採用を決めない。

Phase 13〜16のDSP・シーク経路、Golden WAVは変更していない。追加したC++プログラムとPythonスクリプトは独立した計測器であり、製品再生経路には接続していない。

## 条件と測定方法

- 環境: macOS 26.6.2 / arm64。結果はこの実行環境の一回の計測で、cold cache、他機種、実際のAudio Callbackの期限を保証しない。
- 入力: `results/phase12/golden/input/mix.wav`、44.1 kHz、ステレオ、1,984,500入力フレーム（45秒）。出力は3,969,000フレーム（90秒）。Phase 5.3 Experimental 3500、速度0.50、事前解析済みTimeMap。
- Aの比較基準: 既存 `Phase14PlaybackPipeline::startAtOutputFrame` を変更せず、事前解析後に先頭からDSPを再実行して指定位置まで破棄し、FIFOへ16,384フレームを蓄積。先頭3、中央3、末尾3、連続要求4の計13地点。各地点の先頭4,096フレームをGoldenと照合した。測定区間に事前解析・再生段フェード・デバイス開始/停止は含まない。
- B: 既存 `phase13_stream` でraw WAVキャッシュを生成し、Goldenのファイル全体のSHA-256を照合した。別の独立C++試作では同じ13地点と疑似乱数200地点から、WAV読み込み→planar変換→事前確保済みFIFOへの16,384フレーム書き込みまで計測。先頭4,096フレームをGoldenと照合した。WAV読み込みはOSのファイルキャッシュが効いた可能性が高い。Audio Callbackは動かしていない。
- `median`は中央値、`p95`はソートした値の95%点（nearest-rank）、`max`は最大値。連続要求は直列に安全な状態遷移を行った計測で、同時多発要求の取り消しを意味しない。

## A: DSP状態チェックポイント

チェックポイントは最終出力サンプル `n` の処理を終えた**全解像度とFIRが整合した境界**で採取する。再開時は最も近い `n <= target` の状態を復元し、残りを通常DSPで進め、目的位置から16,384フレームをFIFOへ蓄積する。近傍の入力時刻を単純に2倍した位置は使わず、正規座標は出力サンプル番号とする。入力時刻をUIから指定する場合は固定TimeMapで変換する。

| 状態 | 保存・復元すべき内容 |
| --- | --- |
| TimeMap/解析 | 不変のTimeMap、イベント、reset/strength一覧は共有。ハッシュで同一性を確認。各解像度の`nextFrame_`、`produced_`、`previousStart_`、`pendingAnalysisHop_`、最終出力位置を保存。 |
| Low/Mid/High位相 | 左右の`previousPhase_`、`synthesisPhase_`、初期化/再同期フラグ、前回振幅。Phase Lockingのowner/peakはフレーム境界で再解析可能か確認が必要。ステレオ整合の前回IPD、有効フラグ、重みの累計も保存。 |
| OLA/先読み | 6個のringの未確定signal/weightと各`base_`。各解像度の65,536サンプル循環キャッシュの有効内容と位置。FIRの先読みで各解像度の処理位置が最終出力位置より先行し得る。 |
| FIR | 左右×低域/高域の`accum_`、`base_`、`nextBlock_`。フィルター係数とFFT setupは同一構成から再生成可能だが、畳み込みのブロック位置を厳密に保つ。 |
| 外部条件 | 同一入力バイト列、構成、ソフトウェア/Accelerate環境、同じ演算順。WAV readerの読み取りキャッシュは再構築可能だが、読み出し位置と参照ファイルを保持する。 |

コード上の固定配列容量から、ステレオ1チェックポイントで解像度出力循環キャッシュ約1.50 MiB、OLAのsignal/weight約0.406 MiB、FIR蓄積ring約0.25 MiB、計**約2.16 MiBが下限**。位相、FIR作業状態、インデックス、シリアライズ費用は別。5秒出力間隔なら10分出力に約120件、下限だけで約259 MiB。10秒間隔なら約60件・下限約129 MiB。実容量と復元時間は未計測。間隔を短くするとシーク残余のDSP再実行は減るが、メモリ・生成時のコピー費用は増える。ディスク保管を併用する場合は読込遅延とバージョン管理も必要。

この方式の実装難度は高い。とくにFIRがブロック単位で将来サンプルを先読みし、Low/Mid/Highが同じ最終出力位置で異なる`produced_`を持つ点を見落とすと、復元後の波形がGoldenからずれる。正式DSPを変更しない今回の範囲では状態採取APIを追加せず、推定シーク時間も実測値として示さない。

## B: Golden相当PCMキャッシュ

独立試作は既存DSPを使って0.50倍速の**補正前raw float32 PCM**を生成した。キャッシュ31,752,044バイトのSHA-256は`a729f3764c7a387262ec2c139a1d9bb0ff1a9669fe817ddd837545a9847e01f1`でGoldenと一致。サンプル数、2ch、44.1 kHz、WAV形式も一致した。再生用ヘッドルームゲインや256フレームフェードはキャッシュに焼き込まない。

試作のキーは入力ファイル内容SHA-256、DSP/audioソースの指紋、固定構成の指紋を結合したSHA-256。manifestにはTimeMap hashと出力SHA-256も記録した。製品版のキーと無効化条件にはさらに**DSPバイナリ/ビルドID、コンパイラ、macOS/Accelerate版、TimeMap版・hash、入力のチャンネル/サンプルレート、出力形式、速度**を含める。内容変更、構成変更、環境変更、欠損・サイズ不一致・ハッシュ不一致なら使わない。生成中は別名へ書き、全長・形式・ハッシュ検証後に原子的に公開し、途中停止で部分ファイルを公開しない。今回の試作はこの永続キャッシュ管理・破損時フォールバックまでは実装していない。

44.1 kHzステレオfloat32・0.50倍では45秒入力で約30.28 MiB、5分入力で約201.9 MiB。48 kHzなら5分入力で約219.7 MiB、1時間入力で約2.57 GiB。速度ごとに別PCMが必要で、速度を連続可変にすれば全速度の事前生成は現実的ではない。現行RIFF WAV書き込みは約4 GiB制限があるため、長尺・多速度の製品キャッシュには分割ファイルまたは大容量形式が必要。キャッシュを生成中の再生、容量上限とLRU削除、ストレージ不足時の扱いも別段階で設計する。

## 256フレームフェードとアタック

Phase 16のフェードインは44.1 kHzで5.805 ms、先頭ゲイン0、256番目相当で1。DrumsとMIXの0.50倍Goldenから強いピーク各10箇所を選び、シーク開始位置がピークまたはその2 ms前にある場合の**最初の256フレームのRMS**を数値評価した。これは再生段のみの処理で、raw DSP比較には含めない。

| 音源・シーク位置 | RMS比 中央値 | 10箇所の範囲 |
| --- | ---: | ---: |
| Drums、ピーク上 | 0.562 | 0.473〜0.639 |
| Drums、ピーク2 ms前 | 0.536 | 0.425〜0.634 |
| MIX、ピーク上 | 0.532 | 0.381〜0.621 |
| MIX、ピーク2 ms前 | 0.526 | 0.456〜0.555 |

ピークを含む区間にシークすると短いアタックの最初の約5.8 msが数値上大きく弱まる。特にピーク直上ではそのサンプルのゲインは0。**聴感上の劣化は未判定**であり、クリックが消えたというPhase 16の回答だけでアタック品質まで保証しない。キャッシュ方式を採っても、この再生段フェードの論点は残る。製品判断前にシーク位置をアタック直前/直上へ揃えた実機AB試聴が必要。

## 推奨する段階的実装

1. 既知ファイル・0.50倍速で、Phase 13 DSPからraw PCMを非同期に生成し、キー/ハッシュ/サイズを検証して原子的に公開する。Goldenとのバイト一致を回帰ゲートにする。既存Phase 16経路はそのまま残す。
2. 制御側でキャッシュの有無と有効性を判断し、シーク先のPCMを読み出して既存FIFOへ16,384フレーム先行蓄積する。コールバックにはファイルI/Oや状態破棄を持ち込まない。無効・未生成・読み込み失敗ならPhase 16へ戻る。連続要求は古い準備を取り消し、最後の位置のみ採用する。
3. cold cacheと低速外部ストレージ、3/5/10分音源で準備時間の中央値/p95/最大、生成時間、RSS、容量を再測定し、実機でクリックとアタックを確認する。Golden rawとFIFO値の一致を確認し、再生段ゲインを別に監査する。
4. 任意速度・ストレージ容量制限の要件が定まってから、チェックポイント案を再評価する。採用する場合は新しい独立ブランチ/試作で状態保存→復元の全地点バイト一致を先に立証する。失敗したら製品シークへ入れない。
