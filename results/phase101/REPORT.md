# Phase 10.1 — 有限先読みの過渡音対応リアルタイム時間写像

## 結論

Phase 10 の線形モードを既定のまま残し、`TimeStretchProcessor::prepare(..., RealtimeTransientConfig{true, 128})` で選択する実験的な過渡音モードを追加した。全曲の事前解析は使わない。64 / 128 / 192 ms の固定先読みを選べる。128 msで孤立インパルスとクリックの位置は線形モードよりPhase 5.3に近づいた。ただし0.50倍のクリック列はPhase 5.3の0 msに対して最大間隔誤差15.12 msであり、人工ドラム・雑音バーストの各指標も一様には改善していない。**Phase 5.3と同等の過渡音品質が完成したとは判断しない。** Phase 5.3をオフライン高品質の基準として維持し、リアルタイムモードは別品質として評価する。192 msに延ばしても今回の人工信号では128 msから改善しなかったため、先読みをさらに延ばさない。

## 実装

- Mid 4096/1024 の共有スペクトルから、正の対数スペクトル変化量を求める。直前12フレームの中央値と中央絶対偏差（MAD）で閾値を更新し、局所最大・エネルギー上昇・強度を候補条件にする。検出側の作業配列は `prepare()` 時に確保する。
- 候補の間隔が2 Midフレーム以内なら同じイベントへまとめ、最大5フレームの範囲で最も強いピークを選ぶ。最後の候補の約3フレーム後に確定する。EOSでは利用可能な実サンプルまでを使い、不足する解析窓をゼロで埋める。
- 128 msではピーク前2フレーム、後5フレームを滑らかな余弦肩で囲み、局所時間比を通常の `1/speed` から1.0へ寄せる。MidとLowは同じイベントと時間写像を使い、Low専用検出器は設けない。ピーク時の全bin位相リセットを両解像度に対応付け、左右同時に適用する。選択的なbinリセットは使用しない。
- 高いクレスト比（20以上）と、周囲の次点ピークに対する3倍以上の振幅比がある場合だけ、ピーク近傍3,072サンプルからサンプル位置を確定する。不確かな場合はフレーム位置を使う。イベントの合成位置を全体時間比の理想位置へ寄せ、周囲のフレームへ補正を分配する。
- 過渡音で不足した伸張量を `stretchDebtSamples` として保持し、通常区間で約12 Midホップに分けて返す。実効比は全体比の1.5倍以下、フレーム間の比の変化は0.4以下。密なイベントで返済不能になる場合は、借り時間が入力0.2秒分を超えたところから保護量を減らし、0.4秒分でゼロにする。これにより時間差の無制限な累積を避ける。速度変更時は借り時間を急に消さず、既存の64 ms（48 kHz、3ホップ）速度追従と返済を継続する。`reset()` で検出履歴、未確定候補、イベント、アンカー、借り時間を消す。
- 合成開始位置を一度確定した後は変更しない。Midホップ当たり128サンプル以上、最大 `min(3, 1.5 / currentSpeed) × 1024` サンプルへ制限し、OLAリングの過去への書き込みや窓間隔の過大化を防ぐ。これは密なBassイベントで見つかった異常な振幅増加の修正である。
- WAVを知らないDSPコアと、比較用の `realtime_stretch` CLIを分離した。レンダー側の `pullOutput()` は従来どおりFIFOコピーと不足分のゼロ埋めだけ。FFT、検出、時間写像はDSPワーカーで実行する。

## イベント一致

Phase 5.3の `TransientDetector` と `TransientEventMap` が出すイベントの **Midフレーム中心** を基準とし、±20 msで一対一照合した。128 msモードの0.50倍で、インパルス2/2、クリック19/19、短い雑音バースト3/3、減衰雑音3/3、Bass 28/28、Mix 32/34、Drums 32/38、Guitar 34/37、女性ボーカル15/16、男性ボーカル6/7の対応を得た。適合率はそれぞれ100%、100%、100%、100%、100%、94.1%、84.2%、91.9%、100%、85.7%。人工ドラムは27個のオフラインイベントに対して29個のライブイベントで、適合率93.1%、再現率100%。対応したイベントのフレーム位置誤差は中央値・90百分位とも0 msだった。これは**フレーム単位の検出一致**であり、出力波形のアタック位置の精度とは別である。

## 試聴ファイルと確認点

`results/phase101/ab/` に全11音源×2速度×3方式を作成した。`results/phase101/blind/<音源>_<速度>/A.wav`、`B.wav`、`C.wav` には方式を伏せたコピーがあり、別ファイル `blind_key.csv` に対応表を保存した。客観指標だけでは聴感の優劣を断定しない。Drumsのキック／スネア、Bassのプラック、Guitarのピック、Vocalの子音、Mixのキック／スネア／中央ボーカルを重点的に聴き比べる。特に0.50倍のクリックの残存する時間揺れ、Drumsの高いピーク、Guitarの横方向の広がり、短い雑音の前響きを確認する。

再生成は `scripts/phase101_generate.py`、`scripts/phase101_evaluate.py`、`scripts/phase101_lookahead.py` の順に実行する。後二者にはNumPyを含むPython環境と共有済みの元WAVが必要である。`realtime_stretch` は `--mode linear|transient` と `--lookahead-ms 64|128|192` を受ける。イベントの個別CSVとWAVは生成物として手元に残し、集計CSV・報告書をバージョン管理対象とする。

## 残る問題

1. 128 msでもPhase 5.3のクリック精度・全過渡音品質には届かない。64 msはアンカー精度不足、192 msには今回改善がない。
2. 密なイベントでは借り時間の上限を守るため保護を弱める。これは速度の長期安定を優先する設計で、連打のアタックはオフライン版と異なる。
3. EOSで最終出力サンプル数は要求された全体時間線へ合わせるが、末尾の借り時間が残る場合の内容がオフライン版と一致する保証はない。出力末尾の聴感を追加確認する必要がある。
4. 実際の音声デバイス、Swift/Objective-C++、AVAudioEngine上での遅延・アンダーラン・低レベルCライブラリ内の割り当ては未検証。今回その統合は行っていない。
