# Phase 41 — 0.40→2.00の異常音とワーカー停止の原因調査

## 判定

Phase 40方式CのMIX 0.40→2.00倍速で聞こえた異常音には、**TimeMapが旧0.40倍速の長い合成間隔を保持する間に、Low/Mid/Highの解析ホップだけを半ホップから通常ホップへ先に切り替えていたこと**が強く関係する。元の試聴クリップの約3秒（raw出力の約154,794サンプル）では、実際のMid合成ホップが約3,373サンプル、通常解析ホップは1,024サンプルだった。Hann窓²の重ね合わせ重みの最小値はLow/Mid/Highで約0.011となり、1枚だけの窓が支配する箇所がある。重みはゼロではないためNaNや無音にはならないが、位相ボコーダーの合成に必要な十分な重なりが失われる。

同じTimeMapを保持したまま解析密度を固定する診断WAVで、ユーザーは「改善」と回答した。さらに**TimeMapの遷移が終わるまで半ホップを維持し、その後通常ホップへ切り替える**限定案では、ユーザーがMIXの約3秒の異常音を「聞こえなくなった」、3.7〜4.5秒にも「新たな異常なし」と回答した。Drumsの遅延切替版についても、従来Cとの比較で「違和感なし」と回答した。したがって、解析密度とTimeMapの切替時点の不整合が主因という仮説を支持する。ただし今回の試聴結果を他の音源・速度・密集イベントへ一般化して正式採用したものではない。正式macOS再生経路は変更していない。

## 対照条件と時間写像

Phase 40の方式Cをそのまま比較基準に使い、MIXで0.40→1.00、0.40→1.50、0.40→2.00、0.50→2.00、1.00→2.00を対照とした。元WAVのSHA-256とTimeMapは維持した。解析密度の変更がある前3条件で、合成ホップと窓の重みの低下が速度比とともに強くなる。変更がない0.50→2.00では最小重み約0.177、1.00→2.00では約1.5である。詳細は [`controls.csv`](controls.csv) と各 [`map_mix_*.csv`](.)。時間写像の各行には各解像度の実入力位置、実出力位置、旧・目標・実合成ホップ、前後差、局所速度、イベント位置、解析密度を記録した。

0.40→2.00では、遷移中の最大ホップ前後差が従来Low/Mid/Highで3,524／2,775／693サンプル、遅延密度切替では2,775／1,387／347サンプルだった。密度切替を遷移完了後に移すと、遷移全体の最小Hann²重みも約0.011から約0.81へ上がる。これは波形の欠落を防ぐ方向の客観指標であり、単独では音質の優劣を決めない。

0.40→2.00方式Cの要求出力座標は44,544、公開済み末尾は45,056、変更禁止境界は61,521、TimeMapの適用は入力フレーム46／出力115,006、遷移完了は入力フレーム78／出力184,935だった。従来は入力47,104で通常密度へ切り替えた。遅延案は入力79,872で切り替える。切替直後のMidホップは128→256、Lowは約256→512、Highは約32→64となり、窓長を十分下回る。TimeMap、イベント列、アンカー、位相ロック、FIR係数は同じである。診断用の密度固定版は終盤まで半ホップを維持するためCPU負荷が増え、製品候補にはしない。

[`components_normal.csv`](components_normal.csv)、[`components_hold.csv`](components_hold.csv)、[`components_delay.csv`](components_delay.csv) にはLow/Mid/Highの生波形、LP250(low−mid)、LP3500(mid−high)、最終波形を保存した。切替の影響は単一解像度だけでなく3経路の窓重みと位相に同時に現れる。元入力の自然な包絡との差の全てを「水っぽさ」と同一視しない。出力ピーク全体は3方式とも1.413以下、NaN/Infなし。rawのピークが1.0を超えるのは既存の音質基準と同様で、試聴WAVには共通ゲイン0.40を使用した。

## 限定案の正確性と副作用

生成したraw WAVのハッシュ、長さ、形式は [`manifest.csv`](manifest.csv) に記録した。試聴用WAVは全方式で同一固定ゲイン0.40を使用し、raw DSPの比較と分けている。

遅延切替版のMIX raw WAVは [`mix_040_to_200_C_delay_density.wav`](mix_040_to_200_C_delay_density.wav)。独立オフライン参照 [`mix_040_to_200_C_delay_density_reference.wav`](mix_040_to_200_C_delay_density_reference.wav) とSHA-256が `d95473045186dc243583996302d5d8d2edf0e6ba16cc5fec9cd4502a664d01cb` で一致した。出力は365,440フレーム、公開済み45,056フレームは従来Cと全サンプル一致。従来Cとの差は出力110,848から、密度固定診断との差は179,200から始まる。FIRの先読みで、TimeMap／解析密度の切替座標より前の未公開サンプルに差が生じる。公開済みPCMは変化しない。Drumsも361,359フレームで独立参照とSHA-256 `540165317666fbf456fd92285eb66c3c465a8e9951afa148fca87c4d1903de13` が一致し、公開済み49,152フレームは従来Cと同一、NaN/Infなしだった。比較クリップは [`audition/`](audition/) に共通ゲイン0.40で保存した。

イベント4件の30ms局所ピーク照合は [`attacks.csv`](attacks.csv)。遅延版／従来Cのピーク比は0.919〜1.000で、1件の検出ピーク位置が約12.36ms移動した。ピーク探索では別の局所ピークを拾う可能性があり、これだけでアタック欠落と断定しない。ユーザーはMIX遅延版の異常音消失とDrums遅延版の違和感なしを確認したが、密集イベントを含む全条件での音質合格は未判断。高域方式Bが固定2.00倍速で得た明瞭なアタックを、切替時にも維持する必要がある。

## ワーカー停止・長尺・模擬コールバック

ワーカー処理の各出力ブロックで、壁時計・スレッドCPU、WAV読み取り、FFT、位相、IFFT/OLA、FIR、FIFO待機・書込み、TimeMap計画、履歴mutex待機を別々に計測できるようにした。診断はワーカースレッド内の最大20件だけを事前確保領域に保持し、出力は終了後に行う。C++ `new` の計数は別の計測実行ファイルだけで有効にし、通常シミュレータと正式プレイヤーには入れない。Cの`malloc`やOS内部の確保はこの計数の対象外である。

計測結果は [`profiles/summary.csv`](profiles/summary.csv)、ブロック上位20件は `profiles/*_top20.csv`、模擬コールバックは [`paced/summary.csv`](paced/summary.csv) に記録する。計測ON/OFF、通常負荷と高CPU負荷、MIX/Drumsの3・5・10分で18回実行し、全件EOS、FIFO不足0、書込拒否0だった。最大RSSは19.2〜23.7 MiBで、曲長に比例して増加し続ける兆候はない。100ms超のブロックはON/OFFの両方に現れた。計測ONの最大壁時計はDrums 3分の229.8ms、同ブロックのスレッドCPUは32.8ms。計測OFFにも最大196.2msが現れた。新しい計測版のMIX 3分ではp95 23.45ms、p99 27.71ms、最大141.23ms／スレッドCPU22.53ms、Drums 3分ではp95 23.72ms、p99 26.91ms、最大126.43ms／CPU34.65msだった。以前の1,151msは再現せず、問題は解決済みとは言えない。

| 通常負荷・計測ON | 出力フレーム | 全壁時計／プロセスCPU | 最大RSS | ブロック最大／p95 |
|---|---:|---:|---:|---:|
| MIX 3分 | 4,113,992 | 25.80／25.16秒 | 19.17MB | 75.0／23.0ms |
| MIX 5分 | 6,759,926 | 44.07／42.21秒 | 20.37MB | 207.7／23.6ms |
| MIX 10分 | 13,374,912 | 87.36／84.10秒 | 22.90MB | 177.0／23.4ms |
| Drums 3分 | 4,441,423 | 28.48／27.35秒 | 19.42MB | 229.8／24.4ms |
| Drums 5分 | 7,321,423 | 45.87／44.39秒 | 20.43MB | 145.3／23.8ms |
| Drums 10分 | 14,521,295 | 90.40／88.16秒 | 23.69MB | 131.3／23.8ms |

遅いブロックの大半では「位相」区間の壁時計時間が長い一方、同区間のスレッドCPUは20〜30ms程度だった。例：MIX 5分の最悪ブロックは全体207.7ms／CPU22.9ms、位相区間185.1ms／CPU20.3ms。別のDrums 3分の最悪ブロックは全体229.8ms／CPU32.8ms、位相区間170.8ms／CPU29.3ms、IFFT/OLA区間56.1ms／CPU1.5msだった。したがってDSP演算量の一時的な約200ms増大では説明できない。新計測版の最大FIFO書込み22µs、履歴mutex待機4µs未満、TimeMap計画のスレッドCPU約0.44〜0.46msであり、これらも100ms級の停止を説明しない。重大ページフォルト0のMIXでも141ms停止があった。C++ `new` は上位ブロックで1回／2,048フレーム（ワーカー側で渡す `std::function` の生成と整合）で、数百msの計算停止の直接証拠はない。OSによるスレッドの実行停止が有力だが、スケジューラかライブラリ内部待機かは未確定。Cの`malloc`、デバイスI/O、実機の割込みはこの測定だけで除外できない。

遅延切替案の模擬オーディオコールバックは、MIX/Drumsそれぞれ64・128・256・512・1,024フレームと、512フレームで70%の競合負荷を3回、計16条件を実行した。16/16で終端一致、FIFO不足0、書込拒否0、コールバック処理期限超過0だった。コールバック処理時間の最大は0.826ms、ワーカー壁時計の最大は100.5ms、最大RSSは17.9MB。スレッドの起床遅れは最大25回あり、コールバック内部の処理期限超過とは区別している。要求から適用ノードが模擬コールバックへ到達する時間は中央値1,493ms、p95約1,608ms、最大1,612ms。これは音質改善による短縮ではなく、元の方式Cの応答性をほぼ維持した結果である。macOS実機の安全性を証明するものではない。

## 回帰と次の扱い

Phase 12/28 Goldenの25/25本、Phase 40の低速B・高速Bを含む固定速度70/70本について、保存済みWAVと記録済みSHA-256を照合し一致した。全体ビルド成功、CTestは**48/48成功**（296.44秒）。Phase 39/40の既定は解析密度の即時切替のままなので、既存の結果に変更はない。正式Experimental 3500、Phase 30/36の再生経路、キャッシュ・シーク、Goldenには手を加えていない。

遅延切替は研究用の最小案として残す。方式Cの正式採用や0.40→2.00のリアルタイム統合は行わない。Drumsの試聴では違和感がなかったが、次に密集イベントや他の速度変更でアタック保持を確認し、公開済みPCMの保護、長尺FIFO不足0、ワーカー最悪停止の扱いを満たしてから採否を決める。Phase 39の方式Aはフォールバックとして維持する。

## 再現手順

```sh
cmake -S . -B build
cmake --build build -j4
ctest --test-dir build --output-on-failure -j4
build/phase39_sim results/phase31/input/mix.wav results/phase41/mix_040_to_200_C_delay_density.wav 0.4 1.0:2.0 512 results/phase41/plan_delay_density.csv 2048 C delay-density
build/phase39_reference results/phase31/input/mix.wav results/phase41/mix_040_to_200_C_delay_density_reference.wav 0.4 results/phase41/plan_delay_density.csv C delay-density
python3 scripts/phase41_profile.py
python3 scripts/phase41_paced.py
```

音響診断のPythonスクリプトはNumPyが入った環境で実行する。`phase41_profile_sim` はC++ `new` の計測専用であり、音声比較用の既定実行ファイルとは分けている。入力と比較WAVはローカル保存で、公開Gitには音源を追加しない。
