# Phase 55：段階解析の設計と採用判断

## 判定と対象

**B：条件付きの実現可能性を確認、製品採用は保留。** 閉じたイベントに挟まれたTimeMapと、その手前へ十分に切り戻したPCMは、試験範囲で全曲方式とビット一致した。一方、固定秒数の部分解析をそのまま公開する方式は不一致となった。任意の素材で一定時間以内に最初の区間が閉じる保証はない。長尺全PCM・増分状態の引継ぎ・実時間供給・速度変更を含む一致は未証明であり、Aとは判定しない。

Phase54のPlaybackEngine、公開API、Merodoa契約は維持する。追加した実験は独立実行ファイルだけで、本番用libraryのソースやcallbackを変更していない。詳しい実測と未実施項目は[REPORT](../results/phase55/REPORT.md)、確定条件は[依存関係](PHASE55_ANALYSIS_DEPENDENCIES.md)を参照。

## 1. 候補の比較

| 方式 | 初回の待ち | 正確性・制約 | 今回の扱い |
| --- | --- | --- | --- |
| A 既存全曲解析 | 内容識別→全解析→map→先行蓄積 | 既存の基準 | 維持・性能測定 |
| B 全曲解析を別スレッドで実施 | 受付応答は早いが再生の依存は同じ | アプリのUI応答改善にはなる | 独立wrapperで性能測定 |
| C 固定長部分解析を仮EOSとして再生 | 短いが将来の解析で既出力が変わる | TimeMap・イベント・合成末尾が不一致 | 不採用、反例を保存 |
| D イベント閉鎖単位で確定領域を伸ばす | 素材の閉鎖区間次第。最悪は全曲待ち | 既定mapの閉じた区間は局所計算可能 | 条件付き次Phase候補 |
| E 再生要求前の全曲先読み | 解析が既に完了していればhit | 先読みできた曲だけ。入力寿命が必要 | まず推奨するアプリ側改善 |

## 2. 次Phase候補の構造

```text
検証済み・変更禁止の入力FD / 入力世代ID
    │
    ├─ 逐次解析worker
    │    生の特徴列 → 閾値・検出確定 → イベント閉鎖 → 精密アンカー
    │    → immutable snapshot（検出 / event / map の確定境界を別々に保持）
    │
    └─ DSP worker
         必要な確定map・resetと入力窓を取得
         → 同一インスタンスの位相 / OLA / FIRを継続
         → 既存FIFO → 既存callback
```

解析済みサンプル位置、検出確定位置、閉鎖済みevent、map確定node、合成が安全に参照できる上限、FIFOへ公開済み位置は別の値とする。単一の`analyzedUntil`だけで管理しない。snapshotの末尾を仮EOSとして製品合成へ渡さない。

mapは0→最初の閉鎖peak、その後は前の閉鎖peak→次の閉鎖peakで確定する。連鎖中のeventは保留する。曲末の最後の区間とpaddingは真のEOSまで保留する。既定の補償・アンカー計算をそのまま使い、重みの集計とdouble加算の順序を変えない。未解析領域を一定速度で埋めてから置き換える方式は採用しない。

## 3. 必要な先読みとチャンク

検出はMidの未来2,048入力サンプル、検出flagまでならさらに2Hの保守的余裕、イベント閉鎖は最後の候補から12Hの無候補確認、アンカーはpeak+2Hまで。これらに合成の最大窓とFIRブロックの参照範囲を追加する。イベントの連鎖長と次peakまでの距離には上限がないため、一定秒数の総先読み上限は提示できない。

チャンク境界は絶対H格子に揃え、次チャンクで同じSTFTフレームを違う順で計算しない。WAV読取チャンクと解析確定の単位は分離する。8/32/128などのMidフレーム単位を候補とし、CPU時間・通知回数・一時メモリを実測して決める。Phase55の1.5/2.5/3.5秒等のprefix再解析時間は、状態を継続する増分解析の速度ではない。

FFT/前回logの小さい状態と未閉鎖eventは常駐させる。特徴列を全保持するならメモリは全曲方式に近い。snapshotコピーを無制限に重ねず、DSPが解放した世代を解析・制御側で回収する。容量には使用中leaseを含める。全解析の最終snapshotだけをPhase54の完成キャッシュへ昇格できるようにし、部分結果を既存の「解析完了」エントリとして公開しない。

## 4. 位相・OLA/FIRと供給条件

解析チャンクのたびにDSPを再起動しない。位相、左右の共有ピークと位相距離、OLA信号/重み、FIR履歴とFFTブロック開始を保持する。map nodeの一致に加え、合成で使用する全node・reset・入力窓が確定していることを、Phase36のFrontier相当の境界で確認する。

CandidateのFIFO/先行/生成は16,384/16,384/2,048、Baselineは16,384/12,288/2,048を維持する。解析・DSP間の待ちはworker上だけ。callbackは事前確保FIFOを読む既存動作を維持し、mutex、I/O、確保、解析、snapshotの共有所有権処理、重い状態照会を追加しない。

CPU負荷で解析が追いつかない可能性を隠さない。解析完了量の秒数ではなく、確定済みmapで追加供給できる出力フレーム数を使う。開始前に既定先行量と合成の未来参照が確保できなければ、全曲方式の完了まで待つ。

再生中は、未確定区間へDSPを進めない。確定量が減る前に制御側で待機/再準備を選ぶ。最悪のOS停止を解析方式だけで防げるとはしない。実際にFIFO不足になれば既存callbackは無音埋めと不足記録を行い、音声品質FAILのまま扱う。別の位相初期化・近似mapへ切り替えて不足を隠さない。

全曲fallbackも、使用中の位相へ後から別mapを継ぎ足せるという意味ではない。公開済みprefixと全解析mapの一致を検証し、使用済みnodeが不変と証明できる場合だけ同じ状態で続きを生成する。境界が証明できない場合は安全停止し、全曲方式で先頭から再準備する。開始後の任意時点に無音・遅延なくfallbackできる保証は次Phaseでも独立の評価対象である。

## 5. ライフサイクルと異常時

| 条件 | 必要な処理 |
| --- | --- |
| Stop / 破棄 | 入力世代を失効、解析をチャンク境界でcancel、DSP停止、callback静止後に所有領域を解放。古い結果を公開しない |
| Pause / Resume | 合成とFIFOを保持。解析継続は予算内で可。Resume時に同じ公開順序を維持 |
| EOS | 実ファイル終端でのみpadding・最後のmap・目標長を確定。部分末尾をEndedにしない |
| 入力置換 / 別曲 | FDと選択パスの同一性・世代を再確認。旧曲snapshotを破棄し、明示prepareが必要 |
| 権限失効 | 開いたFDが読める場合と新規openが拒否される場合を区別。アプリの媒体アクセス寿命契約を維持。エラーならFailed |
| 解析失敗 / 読取失敗 | 失敗理由を制御側へ通知。完成キャッシュとして登録しない。無音成功やEOSに変換しない |
| キャッシュ無効化 | 完成・未完成を分離。使用中leaseのデータを解放しない。次の要求から再解析 |
| 同一入力の並行要求 | 世代・固定解析仕様ごとに1解析flightを共有。購読のcancelと全解析のcancelを分離 |
| メモリ不足 | 公開前に確保できなければ失敗。古い未使用snapshotを回収。callbackで確保や復旧をしない |
| CPU競合 | 解析の並列FFT数を増やさずDSPを優先。QoSと同時実行数を実測。先行量を削らない |

これらは設計であり、新しい段階解析workerの競合テストに合格したという意味ではない。既存Phase54のcache/seekテストは既存経路の回帰として実行する。

## 6. 速度変更・シーク

初期版の実験APIは固定速度に限定する。速度変更はL1/L2、保護区間、safe-density、公開済みPCMの境界を維持し、必要な未来区間が閉じていなければ要求を待たせる。要求IDのLatest-Wins/Busy/Cancel契約を変更しない。固定速度で一致したことを、速度変更中の一致へ一般化しない。

シーク先が未解析なら解析の完了を待つ。解析があっても位相状態は得られないため、Phase54の先頭から再構築する正確なfallbackを維持する。局所FFTだけで即時シークできるとはしない。DSPチェックポイントは別Phaseで全状態と速度履歴を保存して検証する。

## 7. 実装の順序とAPI案

まずアプリが曲選択後、再生要求前に既存prepareを専用の直列作業キューで始める案を推奨する。再生ボタン受付後に同じ全解析を別スレッドへ移すだけの場合は、再生待ち短縮と説明しない。先読みのcancel/別曲/媒体FDの寿命はアプリの所有者で管理する。今回Merodoaのコードは変更していない。

本当の段階解析を進めるなら、次の順で製品APIから独立して行う。

1. 既存検出の算術を共有する内部primitiveを一度だけ実装し、1回解析と持続状態の増分解析で全フィールドをビット照合する。`finalize()`の単純再利用は禁止。
2. `ProgressiveAnalysisSession`（仮）のsnapshotに`inputGeneration`、`featureThrough`、`detectorThrough`、`closedEventCount`、`mapThroughNode`、`isFinal`を持たせる。まだ公開APIへ追加しない。
3. 固定速度の`MapPrefixBuilder`（仮）で既定補償の加算順を保持し、複数チャンクサイズで最後まで全nodeをビット照合する。
4. DSPに確定済み解析の補給と参照上限を与える内部実験口を設け、全解像度/FIRの実際の参照が境界を越えないことを記録する。同一インスタンスで3〜5分PCMを最後まで照合する。
5. 全形式・全7速度・Candidate/Baseline、速度変更・Stop/Pause/Resume/EOS・失敗注入の一致を通す。SHAだけでなく最初の不一致サンプルを保存する。
6. Releaseの単独実時間試験で解析/DSPのCPU競合、deadline、最大worker時間、RSS、キャッシュ容量を評価する。Phase54の不合格も保持する。
7. すべて通った後に限り、`prepareAsync`/`preloadAnalysis`等の公開案とsnapshot通知契約をレビューする。既存prepareの成功条件を暗黙に変更しない。

同時に、全曲解析のボトルネックをFFT、WAV読取、閾値走査、アンカー走査へ分ける。独立FFTを並列にしても、左右の加算順やフレームごとのfloat丸め、イベント統合、mapのdouble累積順を変えない。高速化案は既存Goldenを固定したまま全サンプル一致で採否を決める。
