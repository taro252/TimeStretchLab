# Phase 58 Fix：供給停止の原因調査

## 対象と証拠の扱い

基準はコミット `75ae70cecaef2739f744fc21eeecf99da179e18f`。PCM16・Stereo・48kHz、4秒境界素材、2.00倍Candidate、内蔵装置72・48kHz・512フレームを固定した。入力SHAは `5e60e5f416b0d1f83c728887253421e06a2b6114ccb8be427a8bcb892b35f584`。

元のPhase58結果は変更せず、今回の全試行を `results/phase58_fix/` に保存した。測定された非CPU時間と、OSトレースによって分類できた時間を区別する。トレースのない過去の失敗を後からOSのせいと断定しない。

## 保存済み不足との相関

`historical_fifo_correlation.json` はDSP開始・公開とcallbackを同じ経過時刻へ対応付ける。`reproduce_private_input/progressive_19` では計10,240フレーム不足した。

| 出力ブロック開始 | Wall | CPU | 非CPU時間 | 開始時FIFO | 当該ブロック中の不足 |
|---|---:|---:|---:|---:|---:|
| 34,816 | 224.953ms | 27.920ms | 197.033ms | 9,728 | 1,024 |
| 79,872 | 204.135ms | 10.394ms | 193.742ms | 3,072 | 6,656 |

残りの不足は別ブロックにも分布する。最大Wallの1ブロックに10,240フレーム全部を帰属させない。旧ログでは位相処理外やブロック間にも停止があり、OS状態はunknownである。

## 今回取得できたOS状態

### 再生中の停止

`stall_flight100_analysis/summary.json` のrun002、出力81,920～83,968。DSPブロックは1.565483秒に開始し、Wall 88.127ms、CPU 14.577ms、非CPU時間73.550msだった。OS側はRunning 14.522ms、Interrupted 0.046ms、Preempted 73.551msで、公開時刻までの区間を観測できた。

内部の位相処理はWall 66.546ms、CPU 0.209ms、OSのPreempted 66.338ms。該当位相区間のシステム呼出し・ページフォルト・C++ newはいずれも0。位相ループ内のファイル読取りやmutex待ちではなく、実行可能なworkerがCPUから外されていたことを確認できた。

最長の非実行区間63.963msの開始時、workerは優先度31で、優先度37のCodex ServiceのStackSamplingProfilerへ切り替わっている。ただし、この別スレッドが63.963ms全体を占有したことまでは示さない。

このブロック中のcallback要求は4,608フレーム。開始FIFO 14,336 + 生成2,048 − 消費4,608 = 終了11,776で、**この試行自体では不足しなかった**。停止時間だけを不足の実測に読み替えない。

最終版との同一ブロック比較は `same_block_comparison.json` に保存した。入力・速度・preset・出力開始81,920をそろえた最終版3回はWall 13.372/14.475/13.324ms、CPUも同値近傍で、差は計測分解能付近だった。OSの実際の優先度は97。これは同じPCMを作る処理の実行状態が改善した証拠であり、保存済み不足全件のOS理由を推測で補うものではない。

### 再生開始前の停止

`underrun_flight100_analysis_complete/summary.json` のrun022、出力8,192～10,240はWall 209.067ms、CPU 9.712ms、非CPU時間199.355ms。OS側のPreemptedは199.356msだった。最大153.075msの非実行開始時には優先度37のCodex Rendererのworkerへ切り替わった。個別の位相区間でも約155msのPreemptedを確認した。

このブロックの公開は0.575725秒、Readyは0.736890秒、最初のcallbackは0.775313秒である。したがって**再生前の起動遅延の証拠**であり、再生中のFIFO枯渇の再現ではない。ブロック全体では小さなページフォルト4件があり、「全ブロックでフォルト0」とはしない。

## 仮説の切り分け

| 仮説 | 支持する測定・実装上の事実 | 限界・反証 |
|---|---|---|
| A：OSによる非実行 | 実際のPreempted区間が位相処理のWall/CPU差を説明。設定要求QoS25に対し実際の通常優先度31 | 今回の該当試行にFIFO不足はない。保存済み失敗のOS状態は未取得 |
| B：DSP内部の同期 | 通常方式にはSnapshot取得mutexがある | 観測した長い位相区間に同期システム呼出しなし。これが主停止の証拠はない |
| C：入力I/O・フォルト | 通常方式の入力キャッシュ補充はpread。トレース全体にはI/O・フォルトがある | 最長の個別位相区間には該当なし。全素材の全停止を否定しない |
| D：確保・初期化 | 通常方式にはブロックごとの所有関数・Snapshot所有権操作がある | 観測位相停止中のC++ newは0。実時間化の前提として分離したが、この停止の直接原因とは扱わない |
| E：解析とのCPU競合 | 解析とDSPは別workerで同時に動く | 実測した長い切替の相手は別プロセス。解析だけが原因という証拠なし |
| F：FIFO背圧・制御待機 | FIFOが満杯なら2msの有界待機が必要 | 長い位相処理内のPreemptedを説明しない。待機時間は解析待ち・背圧として別記録 |
| G：複合 | 通常優先度の再開遅延に加え、I/O・所有権操作の実時間制約がある | 各要因の寄与率は未測定。すべてをOS非実行へ合算しない |

## QoS調査

`qos_probe/results.json` は非音声の独立プローブである。USER_INITIATEDの設定・再取得は成功したが、初期化前後・最初のDSP処理後・再設定後も実際の優先度31だった。取得したQoSクラス値25は分類コードであり、Machの優先度25という意味ではない。「FFTがQoSを解除する」という証拠はなかった。LatencyCritical活動指定にも優先度改善は見られず、採用しなかった。

## 計測の制約

修正候補V2のOS再計測では、詳細診断領域の初回書込みにZero Fillが37件あった。`v2_diagnostic_faults.json` にOSの呼出し履歴を保存した。合計約132µsであり、約200msの停止とは規模も原因も異なる。容量確保済みでもページ初回アクセスが残っていたため、V3では通常準備で全診断領域を初期化した。`v3_diagnostic_fault_verification.json` の117実時間ブロックではフォルト0。V2の705音声セッションと、この追加修正後の最終試験を版ごとに区別する。

初回の通知待ち設定を誤った試行は音声セッション0件で、計測器の失敗として残した。focused traceの最初の8/20セッションはOS観測窓外であり未観測とする。保存待ちを中断したflight recorderは音声23セッション終了後の操作で、Appleの公式importによる復旧データを解析した。容量不足で途中までのXMLを完全なデータとして使わず、終端を検査して再出力した。

生トレースはbuild内、導出結果とSHA・圧縮復元の記録はresults内にある。1msの待機を要求するスレッド標本は補助情報で、実際の標本間隔はOSに左右される。標本間の長い空白を連続状態の証拠としない。連続した非実行時間の分類にはInstrumentsを使用した。

最終的な修正後結果・原因判定・Gate 1は [検証記録](PHASE58_FIX_VALIDATION.md) と [機械可読判定](../results/phase58_fix/VERDICT.json) を参照する。

最終判定は、供給停止の主要因として通常優先度workerのOS非実行を特定、測定範囲でGate 1合格。過去不足との関連は保存済みの時間相関と同じ処理区間のOS観測を合わせた判断であり、過去全件のOS状態が判明したという意味ではない。V3の585音声セッション、通常300回・高負荷100回、長尺4条件、全PCMと既存製品回帰は合格した。
