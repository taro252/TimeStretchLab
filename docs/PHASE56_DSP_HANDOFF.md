# Phase 57への解析データ引継ぎ契約

## Phase 56で渡せるもの

`ProgressiveAnalysisSession::getSnapshot()`は入力世代、実受信量、確定済み検出フレーム、閉鎖event、精密anchor、要求した固定速度（既定161速度）のTimeMap prefixを共有不変データとして返す。Phase56はこれらの中間・最終結果の完全一致を検証する。**同じDSPインスタンスへ解析を補給する処理、PCM生成、PCMの安全な公開境界は実装していない。**

音程・位相、左右の位相関係、窓の重ね足し（OLA）、帯域フィルター（FIR）、L1/L2、窓の重なり密度を保つsafe-densityは既存仕様を維持する。製品API、FIFO容量と先行量、ゲイン、Merodoaの呼出し契約を変更していない。

## データを受け取る手順

1. 入力所有者は固定したファイル/デコード済みPCMの寿命と世代を持つ。解析を行うproducerは1本。
2. producerがappendInput/advanceAnalysis/finishInputを呼ぶ。チャンクごとに必要ならsnapshotを取得し、制御キュー等でDSP workerへ「新しい確定データがある」と通知する。通知用callbackやworker接続はPhase57側で実装する。
3. workerはshared_ptr<const Snapshot>を自分のスレッドで保持し、世代と終端flagを確認する。音声callbackで共有所有権を増減しない。
4. 前snapshotから増えたdetector/event/anchor/map要素だけを取り込む。過去要素は値を変更しない。暫定特徴列やopen eventを参照しない。
5. 不要になったsnapshotはworker/制御側で解放する。古いsnapshotを全部保存すると解析側の容量上限で失敗する。必要な既確定データだけを有界に保持する。

通知は完了数が変わったときだけでよい。受信量が増えてもeventやmapが増えるとは限らない。世代が異なるsnapshotを既存DSPへ追加しない。0番nodeしかないmapを再生可能と扱わない。

## TimeMapの公開範囲

各seriesは末尾を含まないsizeで範囲を示す。`speedCount`と`speedMicros`に指定された速度だけが存在し、`mapThroughNode=N`ならそれらのnodeは0〜N−1が確定、隣接node間の補間はN−2区間まで可能。要求していない速度のseriesは空。最後のnodeの先へ直線外挿してはならない。入力サンプル位置は1,024刻みのnodeであり、receivedInputFramesとは単位が違う。

一度公開したnodeは完全に不変。新しいsnapshotでも同じindexは同じ整数値になる。閉鎖していないeventの右端や仮EOSを使うmapは渡さない。最後のeventから実EOSまでの区間は、isFinalまで渡さない。

初期固定速度ではCandidateのL2とBaselineのCは同じ座標列を用いる。snapshotの既定161列は0.40〜2.00倍を0.01刻みの昇順。必要な速度だけをsession初期化時に要求でき、各列は要求順に対応する。`mapForSpeed(1250000)`のように整数値で取得し、要求していない速度は例外となる。小数6桁の固定速度指定も受け付けるが、主たる網羅試験は全161速度。各速度を同じ参照式で直接計算し、列同士の補間で別速度を近似してはならない。

## DSPが守るべき、より手前の境界

mapが確定していても、そのnodeまでのPCMをすぐFIFOへ公開できるわけではない。workerは少なくとも次を一体で管理する必要がある。

- Low/Mid/Highの次の入力位置、最後に処理した入力位置、各FFT窓の左右サンプル範囲。
- 各解像度で使うmap補間の両node、イベントの位相resetと強度。
- 継続する位相・前回スペクトル・左右共有ピーク/位相距離。
- OLAの未確定信号と重み、各解像度の確定出力範囲。
- FIRの未処理source、FFT変換ブロックの末尾、畳み込み履歴。
- 入力の実EOS、最終出力長、FIFOに既に公開した出力範囲。

これらが参照するすべての入力・node・eventが確定するまで、DSPをその先へ進めない。Phase55の「16,384出力フレームを切り戻す」実験値を、全速度・任意素材の一般的な安全境界に昇格させない。

DSPを解析チャンク境界で作り直してはならない。位相・OLA・FIRの同じインスタンスを継続し、入力不足はworker側で待つ。音声callbackに解析、ファイルI/O、mutex、確保、重いsnapshot照会を追加しない。既定のFIFO/先行/生成（Candidate16,384/16,384/2,048、Baseline16,384/12,288/2,048）を削らない。

## 速度変更

固定速度prefixの一致を、速度変更中の一致へ一般化しない。新速度の補償に必要な閉鎖区間、L1の既処理境界、L2の保護中の旧ホップ保持、safe-densityの変更可能位置、公開済みPCMを同時に考慮する。

未来の必要区間が未確定なら要求を保留する。Latest-Wins/Busy/Cancelの要求ID・世代契約は既存のまま。速度を変えたmapで既に処理した位相・OLA・FIRを後から上書きしない。全161固定速度の解析試験結果から、途中の速度変更PCMの合格は判断しない。session中に要求速度表を変えるAPIはない。製品で現在・次の速度だけを要求する方法と、全161列を保持する方法ではCPUと容量が異なるため、解析結果を共有する範囲と資源予算を別途設計する。

## EOS、キャンセル、失敗

入力不足は正常EOSではない。finishInputを明示するまでpaddingを追加せず、最後のeventと末尾mapを完成扱いにしない。正常EOSではisFinal=trueとなり、全解析結果と全nodeが参照実装に一致する。

cancelは要求であり、producerの次の境界でisCancelledを公開する。cancelled snapshotの途中の確定データが不変でも、そのsessionの後続PCMを正常EOSとして流してはいけない。完了済みEOSへのcancelは完了を取り消さない。

hasErrorはAllocation/入力不正/読取失敗/入力変更/処理失敗を区別する。失敗時は事前確保した通知用snapshotで直前の確定領域を保持し、isFinalをfalseにする。入力世代を更新し、未完成結果を完成cacheへ登録しない。ファイルの内容・媒体アクセス寿命はアプリ所有者の責務を維持する。

## Phase 57で先に証明すること

最初は固定速度・オフライン・既存FIFOへの未接続の実験から行う。同一DSPを継続しながら、全8形式・全161速度・複数チャンク・3分/5分・境界/EOS・イベント連鎖で、既存全曲解析方式とのPCMフレーム数、全サンプルの生ビット、SHAを照合する。最初の不一致の入力フレーム、event、map、出力サンプルを保存する。

その後に速度変更・キャンセル・入力変更・メモリ不足・解析/DSPのCPU競合、実機callbackと期限を検証する。解析の最初の閉鎖event/区間の時刻と、PCMが生成・先行蓄積・callbackへ到達する時刻を別々に測る。現在も初回SHA-256全内容識別のコストは残る。

任意の長さのイベント連鎖や長い無候補区間では、解析が進んでもmap境界は進まない。固定時間以内の開始保証は与えない。正しさを保てない場合は全曲方式を待ち、安全な状態再構築へ戻る。Phase54の過去の実時間FAILと未保証事項は引き継ぎ、今回の解析試験だけで合格へ変更しない。
